## Находки

### H1. Админка была доступна на публичном порту — **исправлено**
Админка и её API обслуживались тем же сервером, что и публичные эндпоинты; их защищали только пароль, 2FA и (необязательно) список IP. Любой, кто достучался до сайта, мог открыть форму входа и бить по ней.
**Исправление:** два независимых listener-а. Админка слушает только `127.0.0.1:3001`, в публичном приложении её кода нет, nginx отвечает 404 на `/admin` и `/api/admin`, Docker публикует порт как `127.0.0.1:3001`, файрвол закрывает 3000/3001, сервер не запускается при небезопасной конфигурации. Доступ — SSH-туннель.
**Тесты:** публичный порт отдаёт 404/400 на 23 пути × 2 варианта (с валидной админской cookie и без), включая URL-кодирование и `//admin`; сокеты в `/proc/net/tcp` только на loopback; Host-guard; отказ стартовать при `ADMIN_HOST=0.0.0.0`, `ADMIN_PORT==PORT`; статическая проверка docker-compose, Dockerfile и nginx.

### M1. Блокировку аккаунта можно было обойти параллельными запросами — **исправлено**
Счётчик неудач считался из копии строки пользователя, прочитанной до медленного хэширования пароля, а блокировка проверялась по этой же устаревшей копии. В тесте все 30 одновременных попыток были обработаны как обычные неудачи (401), блокировка не наступила: ограничивал только лимит по IP.
**Исправление:** атомарный `UPDATE … failed = failed + 1 RETURNING`, а блокировка перепроверяется после хэширования — запрос, уже «в полёте», не может ни успешно войти, ни подтвердить правильность пароля.
**Тест:** 30 параллельных попыток → после них верный пароль получает 429.

### M2. Оборванная загрузка оставляла «зависший» файл — **исправлено**
Если клиент обрывал соединение посреди загрузки, на диске оставался недописанный файл (по коду поток файла при этом зависал и удерживал дескриптор; для Google Drive — недозагруженный файл). Серия обрывов постепенно съедала бы диск или дескрипторы.
**Исправление:** при обрыве запроса поток файла уничтожается с ошибкой, `put()` удаляет остаток.
**Тест:** обрыв после 200 КБ из 5 МБ → блобов и записей в БД не прибавилось, сервер жив.

### L1. Подмена расширения в имени файла невидимыми символами — **исправлено**
Имя `invoice\u202Egnp.exe.png` (символ U+202E, разворот направления) показывалось как `invoiceexe.png`, а нулевая ширина прятала часть имени.
**Исправление:** удаляются управляющие, bidi- и zero-width-символы, имя нормализуется (NFC), обрезаются точки и пробелы по краям.

### L2. `limit=-1` отключал постраничность — **исправлено**
В SQLite `LIMIT -1` означает «без ограничения»; `/subscribers?limit=-1` и `/audit?limit=-1` отдавали все строки сразу (в тесте 266 вместо максимум 200). Доступно только администратору, но при большой базе ответ становится огромным.
**Исправление:** параметры приводятся к диапазону (1…200 и 1…500).

### L3. Подписка на чужой сайт и приведение типов — **исправлено**
Любой разрешённый origin мог подписать адрес на другой сайт (`asveli.pl` → `site=asveli.shop`), а `email: ["a@b.co"]` превращался в строку.
**Исправление:** Origin должен соответствовать `site`, поля обязаны быть строками.

### Усиления без воспроизведённой эксплуатации
- **Повторное использование TOTP-кода при одновременных запросах:** в тесте не воспроизвелось, но чтение пользователя и запись счётчика были разделены асинхронным шагом. Теперь это синхронное сравнение-и-запись (`UPDATE … WHERE totp_last < ?`).
- **Cookie-таблица без прототипа** (`Object.create(null)`), чтобы cookie с именем `__proto__` или `constructor` не могла ни с чем столкнуться.
- **CSRF:** `Origin` сверяется с заголовком `Host` (вместе с портом) и с `Sec-Fetch-Site`. `SameSite` один не спасает: `localhost:8080` и `localhost:3001` — один и тот же «сайт», поэтому другое локальное приложение могло бы использовать cookie. Тест на «чужой порт» проходит.

## Принятые риски и ограничения (осознанно не менялось)
1. **Ответ 429 для заблокированного аккаунта выдаёт, что такой логин существует**, а кто угодно, достучавшись до панели, может заблокировать админа на 15 минут (5 неверных попыток). Из-за туннеля «кто угодно» теперь означает только того, кто уже имеет SSH-доступ. Блокировка полезнее незнания о причине.
2. **Лимит подписок по IP зависит от nginx:** Node доверяет одному прокси-хопу (`X-Forwarded-For`). Это безопасно, пока публичный порт слушает только `127.0.0.1` и nginx перезаписывает заголовок (так настроено в `docker-compose.yml` и `deploy/nginx-10-https.conf`). Если открыть порт 3000 в интернет, лимит обходится подменой заголовка.
3. **Публичные файлы кэшируются до часа** (`max-age=3600`): после снятия галочки «Публичный» копии в CDN/браузерах могут жить до часа.
4. Ботнет с множеством IP может забить таблицу подписчиков; глобального потолка нет. Следите за размером базы в панели.

## Зависимости
`npm audit --omit=dev`: 4 замечания уровня moderate, **все в транзитивной зависимости `uuid` внутри библиотеки Google** (`@googleapis/drive`): «нет проверки границ буфера в uuid v3/v5/v6, если передан `buf`». Код проекта `uuid` с `buf` не вызывает, поэтому уязвимость недостижима. Исправление требует мажорного обновления `@googleapis/drive` 8 → 26. Я не стал обновлять вслепую: драйвер Drive проверен только на подложном клиенте, а не на реальном Google. Обновлять лучше вместе с проверкой на реальном аккаунте.
Статический анализ: 0 ошибок, 8 предупреждений — разобраны вручную, все ложные (ключи из собственных констант, пути из конфигурации или проверенных 32-символьных id).

## Что НЕ проверялось (честно)
- **Реальный Google Drive**: драйвер тестировался на подложном клиенте (загрузка, диапазоны, лимит, удаление, повторные попытки), но не на настоящем API и квотах.
- **nginx и Docker**: в среде проверки их нет. Файлы `docker-compose.yml`/`Dockerfile`/конфиги nginx проверены статически (разбор YAML, тесты на содержимое), но **не запускались**. Выполните проверки из раздела 4 README после деплоя.
- **Настоящий SSH и файрвол ufw**: туннель имитирован TCP-перенаправлением (тот же механизм), скрипты проверены только на синтаксис.
- Нагрузочные тесты и DoS на уровне сети/TLS; безопасность самого сервера (ОС, SSH, обновления) и вашего компьютера, с которого вы открываете туннель.
- Автоматизированный пентест внешними сканерами (ZAP, nuclei).

## Что сделать вам после деплоя
1. Выполнить проверки «снаружи админки нет» из раздела 4 README (с другого компьютера).
2. Включить 2FA в панели (Безопасность).
3. На сервере: вход по SSH только по ключам, `PasswordAuthentication no`.
4. Настроить бэкап `asveli.db`.
5. Периодически: `npm audit`, обновление Node и образа Docker.

## Addendum — multi-tenancy (org_id)

- Tenant = organisation (`m_orgs`); a store (`m_sellers`) belongs to exactly one organisation and is the workspace. A new store gets its own organisation automatically; staff may attach several stores to one organisation at creation (`org_id`, immutable).
- Every table with a `seller_id` (products, order lines, stock, inbound, ledger, payouts, advances, campaigns, events, seller accounts …) also has `org_id`. SQLite triggers (`src/tenancy.js`) fill it from the store, reject a mismatching value (`tenant_mismatch`) and forbid moving a row or a store to another organisation (`tenant_immutable`), so raw SQL or a forgotten code path cannot break the invariant.
- Seller Central queries filter by `org_id AND seller_id`; a foreign id answers 404. `test/tenancy.test.js` covers DB triggers, cross-tenant API access, multi-store organisations and a lint that fails if a seller-route query on a tenant table lacks `org_id=?`.
- Not tenant-scoped by design: the public storefront (reads approved offers of active stores) and staff in the admin panel (RBAC by role, not by organisation). Per-organisation staff scoping is a later step.

## Addendum — direct AI providers, runtime settings, CI/CD, storefront tests

- AI calls go straight to the provider API (Gemini, OpenAI or compatible, Ollama); there is no separate model service. The key is sent in a header (`x-goog-api-key` / `Authorization`), never in a URL, and error text from the provider is shown with the key redacted.
- **Settings page** (`AI → Подключения AI`): permission `secrets.ai`, deliberately outside every wildcard (`ai.*`, `channels.*`), so only the owner's `*` reaches it. The key is sealed with AES-256-GCM (`DATA_ENCRYPTION_KEY`, bound to its purpose), is write-only (responses carry only `••••1234`), is never written to the audit log, and an unreadable key degrades to "not configured" instead of crashing.
- **SSRF**: a base URL typed in a form is accepted only if it is https, has no credentials/query, and does not resolve to a private, loopback, link-local or metadata address, including IPv4-mapped IPv6 (`[::ffff:7f00:1]` — found and fixed by the tests). Gemini always uses Google's host. `AI_ALLOW_PRIVATE_HOSTS=1` in the server env (not in the UI) is the only way to allow an internal Ollama. Known limit: DNS can change between the check and the call (rebinding); only the owner can set the URL and the response is never reflected beyond a 200-character provider error.
- Photos sent to the model are read only from our own stored public files (never fetched from a URL), ≤ 4 MB, PNG/JPEG/WEBP by magic bytes. A fact taken from the photo is stored with source type `vision`; the card still needs human verification. Generated images are stored as private files and referenced by id.
- Quota: every call (including "Проверить подключение") counts against the daily limit and is visible on the monitoring page; with no key the API answers 503 `ai_not_configured`.
- Storefront bug found by the new tests and fixed: `api(..., { auth: null })` still sent the buyer token. Header/menu buttons also had no accessible name on phones.
- CI: dependency audit (production, high+), secret scan, admin-not-on-public-port smoke check in the built container; deploy pins the SSH host key and rolls back automatically when `/api/health` does not come up.
